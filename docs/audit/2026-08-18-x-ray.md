## 1. Protocol Overview

**What it does:** Two independent escrow vaults for conditional group money — one-shot all-or-nothing campaigns (`GoalVault`) and a pre-determined ROSCA / chit-fund rotation (`RotatingVault`).

- **Users**: Campaign creators/backers; circle organizers/members; Rally relayer (email-wallet + gasless).
- **Core flow**: Deposit exact USDC under a condition; pay the designated recipient only when the condition holds; otherwise every still-held deposit is pull-refundable to its owner.
- **Key mechanism**: Internal accounting + time windows. No shares, no oracle, no AMM. Circles: all-or-nothing *per round*. Goals: all-or-nothing *per campaign*.
- **Token model**: GoalVault locks one immutable ERC-20 (USDC). RotatingVault takes a per-circle ERC-20 (Rally uses the same USDC). No protocol token.
- **Admin model**: RotatingVault is ownerless. GoalVault `Ownable` + a bounded `relayer` for CCTP attribution. No pause, no proxy, no timelock.

### Contracts in Scope

| Subsystem | Key Contracts | nSLOC | Role |
|-----------|--------------|------:|------|
| Goals | GoalVault | 349 | Cross-chain all-or-nothing campaign escrow + CCTP refund rail |
| Circles | RotatingVault, IRotatingVault | 418 | Ownerless ROSCA vault (v2 invite expiry + `claimFor`) |

### RotatingVault v2 delta (`fda38f8`)

- `Invite` typehash adds `expiresAt`; `_EIP712_VERSION` `"1"` → `"2"`.
- `redeemInvite` reverts `expiresAt == 0` (`InvalidExpiry`) and `block.timestamp > expiresAt` (`InviteExpired`).
- `claim()` and new `claimFor(circleId, payee)` share `_claimTo`; transfer + `PotClaimed` always target `payee` (index derived from `_memberIndexPlus1[payee]`).

### How It Fits Together

The core trick: both vaults hold tokens only as named credits and only release them to a hard-coded recipient once a fully-funded condition is met — otherwise the same credits unwind to their depositor.

### GoalVault same-chain fill

```
createCampaign(goal, deadline, beneficiary)
 └─ contribute(id, amount)
      ├─ IERC20.safeTransferFrom(msg.sender → vault)     *credit received, not requested*
      ├─ _credit: raised += received, totalEscrowed += received
      └─ [raised >= goal] withdraw → safeTransfer(beneficiary, raised)
         [now >= deadline && raised < goal] refund → safeTransfer(backer, credited)
```

### GoalVault CCTP fill

```
(Circle TokenMessenger mints USDC to vault — out of scope)
 └─ recordContribution(id, backer, amount, sourceDomain)   *relayer-only; slack must exist*
      └─ _credit (same books)
         └─ miss: refundCrossChain → local safeTransfer / depositForBurn(mintRecipient=backer)
```

### Circle fill → pot

```
createCircle → redeemInvite (anyone submits org EIP-712) → start (organizer, N joined)
 └─ deposit / depositFor → exact depositAmount into current time-derived round
      └─ [roundFundedCount == N] claim / claimFor → safeTransfer(payee, N * A)
```

### Circle break → unwind

```
[last completed round under-funded] _lazyBroken
 └─ markBroken / refund / refundFor
      └─ owed = totalDeposited[m] − claimedCount * A → safeTransfer(member, owed)
```

## 2. Threat & Trust Model

### Protocol Threat Profile

> Protocol classified as: **Vault (conditional escrow / ROSCA)** with **Bridge** characteristics

No share price, no oracle, no borrow. Value risk is bookkeeping + recipient binding + (Goals only) CCTP attribution. Bridge surface is Circle CCTP v2 plus a permissioned relayer that may label already-arrived USDC.

### Actors & Adversary Model

| Actor | Trust Level | Capabilities |
|-------|-------------|-------------|
| GoalVault owner | Bounded (cannot spend `totalEscrowed`; all ops instant, no timelock/pause) | Instant `setRelayer`, `setTokenMessenger`, `setCctpRefundParams`; `rescueExcess` only `balance − totalEscrowed` after `rescueUnlockTime` |
| GoalVault relayer | Bounded (`balance >= totalEscrowed + amount` at credit; cannot choose refund recipient) | Instant `recordContribution` / `refundFor` / `refundCrossChain`; may mis-label real mints (backer, `sourceDomain`) |
| Campaign creator / beneficiary | Bounded (one campaign) | Permissionless `createCampaign`; `withdraw` after `raised >= goal` pays `beneficiary` only |
| Circle organizer | Bounded (per circle; cannot touch escrow after `start`) | `createCircle`, EIP-712 invites, `start`/`cancel` while Filling. No mid-flight abort |
| Member / backer | Trusted for own keys | Approve + deposit/contribute; pull own claim/refund. Invite `member` is where all circle rights accrue |
| Relayer / stranger (permissionless) | Untrusted | May submit `redeemInvite`, `depositFor`, `claimFor`, `refundFor` (circles), `markBroken` — funds still only leave to the bound address |

See [2026-08-18-entry-points.md](2026-08-18-entry-points.md) for the full permissionless entry point map.

**Adversary Ranking** (vault/ROSCA first, then unique bridge):

1. **Compromised / buggy GoalVault relayer** — sole on-chain attestor of CCTP mints; can mis-route *who* is credited, not *whether* USDC exists.
2. **Compromised GoalVault owner** — instant relayer/messenger swap; CCTP refund path follows the new messenger.
3. **Defaulting circle member (early pot)** — inherent ROSCA counterparty risk after a claimed round; later seats eat the default.
4. **Invite / signature attacker** — leaked or replayed organizer EIP-712; v2 adds a deadline so a leak is time-bounded if `expiresAt` is honest.
5. **Malicious circle token / donation sender** — per-circle ERC-20 choice; GoalVault slack donations sit until attribution or post-grace rescue.

### Trust Boundaries

- **GoalVault relayer → credit books** — no timelock; worst instant action is `recordContribution` labeling slack as `(backer, sourceDomain)` (`GoalVault.sol:345-361`). Solvency cap is `balance >= totalEscrowed + amount`. *Git signal: `202de0f` already gated `refundCrossChain` after a High finding on forced burns.*

- **GoalVault owner → CCTP plumbing** — instant `setTokenMessenger` / `setCctpRefundParams` (`GoalVault.sol:248-257`); does not move escrowed USDC except future `depositForBurn` routing.

- **Circle organizer → membership** — signature is admission; after `start` the organizer cannot break or seize (`RotatingVault.sol:271-298`). Funds never belong to the organizer role.

- **Permissionless pull helpers → recipient binding** — `claimFor` / `refundFor` / `depositFor` take a stranger `msg.sender` but credit or pay only the named member (`RotatingVault.sol:316-318,375-377,433-435`).

- **Lazy Active vs stored Broken** — views use `_lazyBroken`; storage flips on first `markBroken`/`refund` (`RotatingVault.sol:417-421,459-464`).

### Key Attack Surfaces

- **CCTP attribution is relayer-shaped** &nbsp;&#91;[I-1](#i-1), [I-5](#i-5), [E-1](#e-1)&#93; — `recordContribution:345-361` credits any `(backer, sourceDomain)` once slack exists. Worth tracing mis-label vs `refund` / `refundCrossChain` recipient and domain routing.

- **Grace window can still move `raised` after `deadline`** &nbsp;&#91;[I-6](#i-6)&#93; — `_requireCreditable:520-524` is `deadline + SETTLEMENT_GRACE`; `_requireOpen:510-513` is strict. Worth confirming whether a grace credit that crosses `goal` is an intended Succeeded flip vs a stranded-mint fix only.

- **`_lazyBroken` is an O(1) induction, not a full scan** &nbsp;&#91;[I-12](#i-12)&#93; — `_lazyBroken:486-492` inspects only the latest completed round; `_firstFailedRound:496-503` is event-only. Worth checking the “no deposit after a failed round” induction across `deposit` / time warp / `memberTarget` boundaries.

- **v2 invite deadline is organizer-chosen** &nbsp;&#91;[I-9](#i-9)&#93; — `redeemInvite:250-251` rejects `expiresAt == 0` and elapsed time; nothing caps `expiresAt` at `type(uint256).max`. Worth checking off-chain signing (far-future = v1-like leak lifetime) and that `expiresAt` is inside the typehash (`_hashInvite:531-538`).

- **v2 `claimFor` force-finalizes a funded pot** &nbsp;&#91;[I-8](#i-8), [E-4](#e-4)&#93; — `_claimTo:379-400` increments `claimedCount` before `safeTransfer(payee, pot)`. Worth comparing dissolution-on-break (`claimedCount` floor in `_refund:447-452`) with a stranger pulling a still-unclaimed funded pot.

- **GoalVault owner CCTP knobs are instant** — `setTokenMessenger` / `setCctpRefundParams` have no delay; `refundCrossChain:447-455` `forceApprove`s the current messenger. Worth tracing a messenger swap mid-refund loop.

- **Custom EIP-712 domain (not OZ `EIP712`)** — hand-rolled cache + fork rebuild (`RotatingVault.sol:509-525`) because OZ 5.6 `Bytes.sol` emits Cancun `mcopy`. Worth matching `inviteDigest` / `eip712Domain` (version `"2"`, fields `0x0f`) to the frontend signer.

- **ROSCA early-pot default is out of contract scope** — header trust notes (`RotatingVault.sol:66-78`): claimed pots stay claimed; later seats carry counterparty risk. Worth treating as mechanism, not a missing `require`.

- **Per-circle token is ungoverned** — `createCircle:198` only rejects `address(0)`; exact-delta check (`_deposit:338-340`) refuses fee-on-transfer. Worth listing rebasing / blacklist / callback tokens as unsupported (stated) and confirming no path credits without the delta.

- **Permissionless `createCampaign` extends `rescueUnlockTime`** — `createCampaign:310-311` has `DeadlineInPast` but never `DeadlineTooFar` (error exists unused at `GoalVault.sol:190`). Worth checking far-deadline grief of `rescueExcess` only — escrow itself is untouched.

### Upgrade Architecture Concerns

None. Both vaults are non-proxy, non-UUPS, no `initialize`. v2 is a new implementation + new domain version, not an in-place upgrade.

### Protocol-Type Concerns

**As a Vault (conditional escrow / ROSCA):**
- Pot math is `depositAmount * memberTarget` with a create-time overflow reject (`RotatingVault.sol:204,396`) — no share rounding to check, but the refund floor `claimedCount * depositAmount` must stay aligned with “every claimed round was funded by all N”.
- GoalVault `_credit` / `_refund` / `withdraw` are the only `totalEscrowed` writers — donation to the vault does not mint credits unless the relayer attributes slack.

**As a Bridge:**
- `depositForBurn` uses `mintRecipient = _toBytes32(backer)`, `destinationCaller = 0` (`GoalVault.sol:447-455`). Worth confirming Circle fee/`maxFee` cannot reduce the destination mint below the amount already subtracted from `totalEscrowed`.

### Temporal Risk Profile

**Deployment & Initialization:**
- GoalVault constructor sets immutable `token` / `LOCAL_DOMAIN` and initial `relayer`/`owner` (`GoalVault.sol:229-236`); deploy script pins Arbitrum Sepolia USDC + domain 3.
- RotatingVault constructor only caches the EIP-712 domain (`RotatingVault.sol:184-187`). Empty-state has no first-depositor share attack (no shares).

**Deprecation (v1 live → v2 coded):**
- Live Circles vault `0xdd9b…` is v1 (no `expiresAt`, no `claimFor`). v2 signatures will not verify there (typehash + version). Residual v1 pots/refunds stay on the old address; unused v1 invites do not replay on a new v2 deploy (`verifyingContract` + version `"2"`).

### Composability & Dependency Risks

**Dependency Risk Map:**

> **Circle CCTP v2 TokenMessenger** — via `GoalVault.refundCrossChain` → `depositForBurn`
> - Assumes: burn of `amount` yields a mint to `mintRecipient` on `destinationDomain`
> - Validates: messenger non-zero for remote domains; `mintRecipient` hardcoded to backer
> - Mutability: owner-replaceable (`setTokenMessenger`)
> - On failure: revert (loop does not skip a failed domain)

> **USDC (GoalVault immutable; RotatingVault per-circle)** — `safeTransfer` / `safeTransferFrom` + GoalVault credit-by-received / RotatingVault exact-delta
> - Assumes: no rebase, no silent fee (RotatingVault), transfer reverts or is SafeERC20-wrapped
> - Validates: GoalVault `received != 0`; RotatingVault `delta == depositAmount`
> - Mutability: USDC proxy (Circle); circle token chosen by organizer
> - On failure: revert

> **OpenZeppelin ECDSA v5.6.1** — `RotatingVault.redeemInvite` recovery
> - Assumes: malleability-checked `ecrecover`; organizer is an EOA / EIP-7702 EOA (no ERC-1271)
> - Validates: `recover == c.organizer`
> - Mutability: internalized lib copy (not a live upgrade)
> - On failure: `InvalidSigner`

**Token Assumptions** *(unvalidated only)*:
- Rebasing / blacklist / pausable ERC-20: not handled beyond SafeERC20 — circle accounting can drift or freeze if organizer picks one.
- GoalVault assumes USDC `transfer`/`transferFrom` deliver the credited amount after `contribute`’s balance-delta.

**Shared State Exposure:**
- Vaults do not share storage. Both may hold the same USDC. CCTP mints to GoalVault only; RotatingVault never sees CCTP.

## 3. Invariants

> Restated here (this drop has no separate `invariants.md`). On-chain=**Yes** unless noted.

### GoalVault (unchanged by v2)

#### I-1

`Conservation` · On-chain: **Yes**

> `token.balanceOf(vault) >= totalEscrowed` at all times.

**Derivation** — NatSpec: `GoalVault.sol:54-62` — *"`token.balanceOf(address(this)) >= totalEscrowed` (always)"*; `_credit` `Δ(totalEscrowed)=+amount` only after slack check or a measured `contribute` receive; `withdraw`/`_refund`/`refundCrossChain` `Δ(totalEscrowed)=−paid` then transfer/burn.

**If violated** — withdrawals/refunds could exceed vault cash.

#### I-2

`Conservation` · On-chain: **Yes** *(ghost-checked in `GoalVaultFuzz`)*

> `totalEscrowed == Σ credited − Σ withdrawn − Σ refunded` over the vault lifetime.

**Derivation** — Δ-pair: `_credit:470-471` ↔ `withdraw:378-379` / `_refund:496-497` / `refundCrossChain:430-431`.

#### I-3

`Conservation` · On-chain: **Yes**

> Per campaign, `raised == Σ amounts ever passed to `_credit`` (refunds do not decrement `raised`).

**Derivation** — Δ-pair: `_credit:470` is the only `raised` writer.

#### I-4

`StateMachine` · On-chain: **Yes**

> `withdrawn` is one-shot: `false → true`, no reverse.

**Derivation** — edge: `AlreadyWithdrawn` then `c.withdrawn = true` (`GoalVault.sol:372-378`).

#### I-5

`Bound` · On-chain: **Yes**

> Relayer cannot increase `totalEscrowed` past `token.balanceOf(this)`.

**Derivation** — guard-lift: `balance < totalEscrowed + amount → UnattributedFunds` (`GoalVault.sol:359`); only `_credit` writes `totalEscrowed` upward.

#### I-6

`Temporal` · On-chain: **Yes** *(two clocks)*

> Same-chain `contribute` requires `now < deadline && !withdrawn`. Relayer `recordContribution` requires `now < deadline + SETTLEMENT_GRACE && !withdrawn`.

**Derivation** — temporal: `_requireOpen:512` vs `_requireCreditable:522-523`.

#### E-1

On-chain: **Yes**

> Relayer cannot conjure funds, inflate `raised` beyond deposited USDC, or drain via withdraw/refund math.

**Follows from** — `I-1` + `I-5` + `I-3` + beneficiary-only `withdraw` + backer-only refund recipient.

#### E-2

On-chain: **Yes**

> A refund pays exactly `_contributedTotal[id][backer]` to that backer (local) or burns to that backer’s bytes32 (CCTP).

**Follows from** — `_refund:490-506` (`to == backer`); `refundCrossChain:450`.

### RotatingVault (v2-relevant restated)

#### I-11

#### I-12

**Derivation** — `RotatingVault.sol:391`.

#### I-13

`Bound` · On-chain: **Yes**

> A deposit credits `depositAmount` iff the vault’s token balance rose by exactly that amount.

**Derivation** — `RotatingVault.sol:338-343`.

#### E-4

On-chain: **Yes** *(v2; `invariant_noStrayPayout`)*

> Permissionless `claimFor` never pays `msg.sender` unless `msg.sender == payee`.

**Follows from** — `I-8`.

#### E-5

On-chain: **Yes**
